# 本地 Hook 核验

本页帮助区分三个问题：插件是否已启用、Hook 脚本是否运行、Agent 是否实际采用维护职责。它们需要不同证据，不能仅凭开关或一条日志互相替代。

## 准备可核验的本地线程

先按 [安装指南](installation.md) 检查运行环境与信任。命令 Hook 需要本地编排；云编排的 dots/Work Cloud 不支持本地插件命令 Hook，即使工具在电脑上执行。依据见 [官方支持说明](https://learn.chatgpt.com/docs/hooks#managed-hooks-from-requirements-toml)。

在专用测试 Git 仓库中使用已安装的插件，保留正常沙箱与审批。Codex CLI 提供 `/hooks` 审查定义；不假定所有 App 版本有相同的命令或日志界面。CLI 核验的结果也不能证明 App 线程执行了 Hook。更新后检查宿主显示的实际定义及待审状态，不手工填信任哈希。

## 启用并读取事件

把 diagnostics 合并到测试仓库已有的 `.repo-knowledge.json` 中，不覆盖其他配置。没有文件时可创建：

```json
{ "version": 1, "diagnostics": true }
```

重新开始本地线程，让 SessionStart 在启用诊断后运行。成功写入诊断时，它的 systemMessage 会向宿主 UI 或事件流提供读取器 argv，包含宿主实际使用的数据位置。该消息不保证自动送达模型；操作者可把真实显示的参数复制给 Agent。参数是 JSON 数据，应逐项正确引用，不能直接当作 shell 文本 eval。

可以向该线程提出：

```text
请只检查 Repo Knowledge 的诊断。若能取得本线程实际提供的 diagnostics
reader argv，按参数读取一次并说明事件及证据边界；若没有，请明确说明。
不要猜数据目录、扫描其他会话或手工运行 hook.mjs。
```

任务结束后再读取一次，才能观察上一回合的 Stop。当前回合尚未结束时，没有它的 Stop 属于正常情况。

若已从该线程或宿主可信信息中取得真实路径，也可在终端读取：

```bash
node /path/to/installed/plugin/scripts/rk.mjs diagnostics --cwd /path/to/test-repo --data-dir /actual/host/PLUGIN_DATA
```

三个路径都必须来自已确认的信息。源码目录、doctor 输出或自行创建的临时目录不能代替宿主数据目录；本文不提供猜测的 App 日志位置。

读取器的退出码不能单独证明读到了诊断：配置或状态不可用时也可能正常退出并返回 `status: "unavailable"`、固定的 `errorCategory` 和空事件。先看 JSON 的 `status`，再看 `enabled` 与 `events`。`status: "read"` 但事件为空只表示读取成功且没有返回记录；关闭诊断后仍可能读到之前保留的事件。

## 判断事件与维护效果

事件记录包含 UTC 时间、事件名、白名单来源、阶段和固定结果类别：

| 字段或结果 | 能说明什么 |
| --- | --- |
| started | 有效事件到达了诊断代码 |
| completed | 事件处理已返回结果 |
| context-produced | 生成了维护职责上下文 |
| reminder-produced | 生成了收尾提醒 |
| warning-produced / no-op | 返回提示或正常放行 |
| failed / runtime-error | 处理失败；不记录原始错误文本 |

completed 在标准输出写入之前记录，所以单靠它不能证明宿主收到上下文，更不能证明模型采用了规则。手工运行脚本也会产生记录，不能拿这种记录冒充宿主原生事件。恢复和压缩须使用宿主真实的 resume/compact 操作；普通续聊不能替代。

宿主报告的单个 Hook 执行耗时与整轮任务耗时不同。排查慢任务时，分别看 Hook 完成事件、模型响应或重试、工具执行及任务截止时间；没有这些证据时，不把全部等待时间归因于插件。

正常功能核验可以使用一个普通小任务：先确认原生启动与 Prompt 事件，再检查 Agent 是否读取适用规则、维护真正拥有内容的文档，并在需要时报告状态。结束后检查原生 Stop 与宿主保存的当前快照回执；Stop 的 no-op 本身不等于回执成功。只读任务应保持项目不变，也不要求维护状态。人工遗漏状态等辅助分支的测试方法与已有结果见 [测试说明](../testing.md) 和 [验证记录](../../VERIFICATION.md)，无需在日常任务中故意省略状态。

没有日志不能直接推出未信任或未执行：诊断未启用、配置或输入无效、缺少 Git 根、安全数据目录不可写、锁冲突或写入失败都可能没有记录。没有提醒也不等于故障；无变化、已有回执、缺少稳定回合标识、关闭跟踪或检查不完整时都可能正常放行。

## 数据范围与关闭

诊断按项目散列隔离，保留最新 128 条，读取上限 32 KiB。记录不含提示、文件内容、会话 ID、任意错误文本、路径或密钥，不是完整审计日志。写入失败不会阻止任务，也不修改业务仓库。

结束核验后，将 diagnostics 设为 false 或移除此项，后续事件便不再写入。关闭不会清除已有数据；确需清理时，先结束相关线程，再只删除已确认属于本插件的目标诊断记录。运行数据的其他边界见 [配置说明](configuration.md)。
